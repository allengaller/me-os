# 02 — 目标人群与 JTBD（Personas & Jobs-to-be-Done）

> 回答「卖给谁、TA 雇 MeOS 完成什么任务、从哪里触达、什么会让 TA 流失」。
> 画像基于产品能力与创始人触达能力推断，Phase 1 结束后用真实用户访谈（见 [docs/INTERVIEW_PLAYBOOK.md](../docs/INTERVIEW_PLAYBOOK.md) 的访谈方法）校准。

---

## 一、ICP（理想客户画像）

**共同特征**：同时满足「有多个数据源散落各处 + 有复盘/梳理习惯或意愿 + 能接受自托管或 Docker」。
**首选切入点**：技术社区里的 AI 尝鲜者与生产力极客 —— 他们是意见放大器，且对 MVP 粗糙度容忍度最高。

## 二、三类核心画像

### Persona 1 · AI 尝鲜者（首发人群）

| 维度 | 描述 |
|---|---|
| 是谁 | 玩过 Claude/Cursor/MCP 的开发者或重度 AI 用户，TA 的 AI 工具链已经很长的延伸 |
| 现状与痛点 | AI 很强但「不了解我」；每次都要手动粘贴上下文；生活数据（睡眠/聊天/笔记）完全不在 AI 可及范围 |
| JTBD | **「当我要让 AI 帮我做周复盘时，我想让它直接读我本周的真实数据，而不是凭我回忆。」** |
| 触发事件 | 看到一篇「MCP 读生活数据」的 demo（这正是 MeLog 技能报告的天然演示场景） |
| 价值匹配 | MCP Server + MeLog Standard 是对 TA 的直接卖点；数据主权是加分项 |
| 触达渠道 | Show HN、V2EX、即刻「一起搞 AI」圈、MCP 生态目录、GitHub Trending |
| 转化路径 | demo 视频/GIF → clone 或 Docker 起服务 → `melog_ingest_entries` 或连接器推第一批数据 → 运行 `health-insight` 技能拿到第一份报告（aha moment） |
| 流失风险 | 连接器覆盖不足（TA 的数据源没被支持）、MCP 配置门槛 —— 对策：一键 MCP 配置复制、连接器路线图公开征询 |

### Persona 2 · 生产力极客 / Life OS 玩家（口碑放大器）

| 维度 | 描述 |
|---|---|
| 是谁 | 用过 Notion 模板/Obsidian/GTD 工具的深度效率爱好者，笔记软件换了五六轮 |
| 现状与痛点 | 模板好看但没有数据自动进来，坚持记录靠意志力，三次后弃用；数据分散在多 App 无法综合看人生状态 |
| JTBD | **「当我想认真管理人生时，我想要一个不用我天天手动搬运数据、又有方法论的仪表盘。」** |
| 触发事件 | 又一次弃用某模板后搜索「local-first life os」「个人数据管理系统」 |
| 价值匹配 | MeLog 自动汇入解决「记录靠意志力」；五维框架解决「有数据没方法」 |
| 触达渠道 | 少数派、小红书效率博主、B 站效率区、即刻「生产力」圈子、播客（看理想/科技早知道类） |
| 转化路径 | 内容种草 → Landing page → db:seed 示例数据 5 分钟看到完整仪表盘 → 迁移自己的领域与目标 |
| 流失风险 | 移动端缺失（打卡场景断）、导入旧数据麻烦 —— 对策：CSV/Markdown 导入、PWA 或快捷方式过渡 |

### Persona 3 · 知识工作者 / 个人品牌经营者（商业价值最高）

| 维度 | 描述 |
|---|---|
| 是谁 | 独立开发者、内容创作者、咨询/自由职业者 —— 创始人自媒体的天然观众 |
| 现状与痛点 | 输入（阅读/经历）和输出（内容）之间断链；选题靠灵感；个人资料、渠道数据、作品散落各处 |
| JTBD | **「当我持续输出内容时，我想让生活的原始素材自动沉淀为选题和作品资产。」** |
| 触发事件 | 看到创始人 build-in-public 内容 —— 「我用自己写的系统经营自己的品牌」本身就是最有说服力的案例 |
| 价值匹配 | 品牌板块（内容流水线/渠道矩阵/作品库）+ MeLog 素材汇入；认知板块沉淀课题 |
| 触达渠道 | 创始人自有渠道（B 站/小红书/公众号/视频号，见 [docs/brand/ACCOUNT_LAUNCH.md](../docs/brand/ACCOUNT_LAUNCH.md) 平台选择） |
| 转化路径 | 内容 → GitHub → 品牌板块 demo → 全产品使用 |
| 流失风险 | 品牌板块学习成本、无协作/多端 —— 对策：内置品牌板块示例数据、作品库公开页（Phase 2 候选功能） |

## 三、画像 → 阶段匹配

| 阶段 | 主攻画像 | 为什么 |
|---|---|---|
| Phase 0–1 | Persona 1 + 2 | 技术社区冷启动成本最低，反馈质量最高 |
| Phase 2 | Persona 2 为主，Persona 1 转化留存 | onboarding 与移动端补齐后才能吃效率人群 |
| Phase 3–4 | Persona 3 | 付费意愿最强，且与创始人 IP 渠道完全重合 |

## 四、反人群（不为谁优化）

- 企业团队（协同、权限、合规需求完全不同）
- 纯小白「不想碰任何技术」的用户 —— 在云托管（Phase 4）之前不主攻，避免 onboarding 崩坏
- 数据套利者/灰产（chatlog 类数据源的合规边界见 [packages/connectors/README.md](../packages/connectors/README.md)，宣传中始终保持「仅处理自己合法持有的数据」表述）

## 五、验证计划（Phase 1 必做）

1. 每个画像完成 ≥ 5 次深度访谈（复用访谈手册的田野调查方法，把用户当受访者）
2. 记录 JTBD 原话，回填本文件的「痛点/触发事件」栏
3. 找到每个画像的「aha moment」统计口径，写入 [06-metrics.md](./06-metrics.md) 漏斗
