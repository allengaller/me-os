# 台词准备（Script Prep）设计文档

- 日期：2026-09-13
- 状态：设计已批准，待实现
- 板块定位：MeOS 顶层入口「台词」，路由 `/scripts`，与方向/行动/认知/反思/资源/MeLog/品牌并列

## 1. 背景与目标

「准备台词」= 把要说的话逐段写好、练到能念顺。三类场景共用一套能力：

1. **短视频口播稿** — 从品牌内容流水线的选题带出核心观点与大纲，受目标时长硬约束
2. **演讲 / 汇报 / 约聊** — 周复盘发言、OKR 汇报、一对一约聊的发言提纲，不发布、不进流水线
3. **播客 / 对谈脚本** — 分段 + 说话人，含开场钩子与转折句

一期四大能力（已确认「都要」，按 §10 分三段落地）：**结构化模板槽位**、**逐段多候选版本对比采用**、**提词器排练视图**、**AI 生成初稿**。

这四项收敛为一套模型 + 一个视图 + 一个端点，不是四个独立功能：槽位是 `ScriptBeat.kind`，候选版本是 `ScriptBeat.alternatives`，提词器是 `Script` 的一个全屏只读视图，AI 生成是 `POST /scripts/generate`。

已确认的关键决策：

- **独立顶层板块**（方案 A），否决「挂 `/brand` 第 7 个 tab」和「扩写 `ContentItem.outline`」两条路
- 否决复用 `ContentItem`：它是品牌语义（带 `pillarId` / `publishDue` / `distributions`，状态机 idea→drafting→ready→published），为「周复盘发言」建一条 ContentItem 会让流水线混进永不发布的记录
- 与品牌选题**单向可选关联**（`Script.contentId → ContentItem`），不关联 Topic / Goal / Reflection
- **候选版本存 JSON 串**而非第三张表，与仓库既有做法一致（`ContentItem.tags` 逗号分隔、`MeLogEntry.payload` 存 JSON）
- 抽 `packages/api/src/lib/llm.ts` 收口 LLM provider 与调用，MeLog 与本模块共用

## 2. 非目标（一期不做）

- 不做 IndexedDB 本地模式。`apps/web/src/lib/localDB.ts` 无任何 brand store，`api.ts` 的 `routeHandlers` 亦无 brand——品牌板块本来就只在远端模式可用，本板块沿用同一边界
- 不做富文本/markdown 编辑器，台词是纯文本（念的东西不需要排版）
- 不做逐段 AI 改写（v1 只有整篇生成初稿，人工改）
- 不做提词排练记录的持久化与历史曲线（退出提词器只提示本次用时，不写库）
- 不做 TTS 音频合成、不做自动发布、不做多人协作
- 不改 `MELOG_LLM_*` 环境变量名。抽为全局共用后名字不再贴切，但改名会破坏用户既有配置，本次仅接受这一命名瑕疵

## 3. 数据模型

在 `packages/api/src/prisma/schema.prisma` 的「品牌 (Brand)」区段之后新增「台词 (Script)」区段，并在 `User` 模型补充反向关系（沿用现有全量罗列风格）。

### Script — 台词稿

| 字段 | 类型 | 说明 |
|---|---|---|
| id | String @id @default(uuid()) | |
| userId | String | 归属 |
| title | String | 台词稿标题 |
| scene | String | `short-video` / `talk` / `podcast` |
| status | String @default("draft") | `draft` / `ready` / `used` / `archived` |
| occasion | String? | 场合：「周复盘发言」「抖音 60s」「对谈嘉宾」 |
| audience | String? | 受众 |
| contentId | String? | 软关联品牌选题，`onDelete: SetNull` |
| targetSec | Int? | 目标时长（秒） |
| wpm | Int? | 语速（字/分钟）。三场景差异明显且时长约束是本板块核心，故按稿存储；为空取 `DEFAULT_WPM_BY_SCENE` |
| notes | String? | 临场提醒（不念出来） |
| order | Int @default(0) | |
| createdAt / updatedAt | DateTime | |

约束与索引：`@@index([userId, scene])`、`@@index([userId, status])`、`@@index([contentId])`。关系：`user` Cascade、`content` SetNull、`beats` 一对多 Cascade。

### ScriptBeat — 台词段（同时承担「槽位」与「候选版本」）

| 字段 | 类型 | 说明 |
|---|---|---|
| id | String @id @default(uuid()) | |
| scriptId | String | 关联 Script，Cascade |
| kind | String @default("body") | 段类型，见枚举 |
| role | String? | 说话人：「我」「嘉宾」「主持人」，对谈场景用 |
| text | String | **当前采用版本** |
| alternatives | String? | JSON 数组 `[{ id, text, note }]`，历史候选 |
| cue | String? | 提示：镜头 / 动作 / 道具 / 语气，提词器弱化显示 |
| order | Int @default(0) | |
| createdAt / updatedAt | DateTime | |

约束与索引：`@@index([scriptId, order])`。

`ScriptBeatAlternative`（`alternatives` JSON 数组的元素类型，也是 shared 导出项）：

```ts
export interface ScriptBeatAlternative {
  id: string;
  text: string;
  note?: string;
}
```

**枚举**（`packages/shared/src/index.ts`，紧接 Brand 段之后）：

```ts
export type ScriptScene = 'short-video' | 'talk' | 'podcast';
export type ScriptStatus = 'draft' | 'ready' | 'used' | 'archived';
export type BeatKind =
  | 'opener' | 'hook' | 'pain' | 'value' | 'proof'
  | 'turn' | 'qa' | 'cta' | 'closer' | 'body';
```

**场景模板**（`SCENE_TEMPLATES`，前端常量，AI prompt 与新建时共用同一份）：

| scene | 槽位序列 | 默认语速 |
|---|---|---|
| `short-video` | hook → pain → value → proof → cta | 240 字/分 |
| `talk` | opener → pain → value → proof → qa → closer | 200 字/分 |
| `podcast` | opener → hook → value → turn → value → closer | 210 字/分 |

新建时按模板一次性生成空槽位（`text` 为空串），模板外的自由段落用 `body`。

**时长口径**（`apps/web/src/lib/scripts.ts` 纯函数，列表与编辑器共用）：

- `countSpeechChars(text)` = 去除所有空白后的字符数（中文按字计，仅计 `text`，不计 `alternatives` / `cue` / `notes`）
- `estimateSeconds(script)` = 全段 `countSpeechChars` 之和 ÷ `wpm` × 60
- `isOverBudget(script)` = `targetSec` 有值且 `estimateSeconds > targetSec × 1.1`（留 10% 容差，念稿普遍比估时慢）

## 4. API 设计

新增模块 `packages/api/src/modules/script/`，文件结构对齐 brand：`routes.ts` / `service.ts` / `constants.ts` / `routes.test.ts`。

注册：`packages/api/src/server.ts` 加 `server.register(scriptRoutes, { prefix: '/api/scripts' })`，紧接 brandRoutes 之后。全部路由 `{ onRequest: [fastify.authenticate] }`，`userId` 取 `request.user.userId`。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/scripts?scene=&status=&contentId=&q=` | 列表，`include: { beats: orderBy order asc }`，`orderBy: [{order asc},{updatedAt desc}]`；`q` 为 title contains |
| POST | `/scripts` | 201 `{ script }`；可带 `beats` 数组一次建稿与槽位 |
| GET | `/scripts/:id` | 单稿含 beats |
| PATCH | `/scripts/:id` | `{ script }`；`updateMany` 按 id+userId，0 行 → 404 |
| DELETE | `/scripts/:id` | `{ success: true }`；`deleteMany` 0 行 → 404 |
| POST | `/scripts/:id/beats` | 201 `{ beat }`；`order` 未传则追加末尾 |
| PATCH | `/scripts/beats/:id` | `{ beat }`；先按 id+userId 校验归属 |
| DELETE | `/scripts/beats/:id` | `{ success: true }` |
| PATCH | `/scripts/:id/beats` | `{ success: true }`；body `{ beatIds: string[] }` 整序，逐个写 `order` |
| POST | `/scripts/beats/:id/adopt` | `{ beat }`；body `{ alternativeId }`，旧 `text` 回写进 alternatives、选中项进 `text` |
| POST | `/scripts/generate` | `{ title, scene, beats }`，**不落库**，前端预览后再 POST /scripts |

**`scriptCreateSchema`**（zod，字段长度上限沿用 brand 风格）：`title` 1–200、`scene` 枚举、`status` 枚举 optional、`occasion` ≤100、`audience` ≤100、`contentId` optional nullable、`targetSec` int 1–3600 optional nullable、`wpm` int 60–600 optional nullable、`notes` ≤2000、`order` int optional、`beats` 可选数组（`kind` 枚举、`text?`、`cue?` ≤500、`role?` ≤50）。`scriptUpdateSchema = createSchema.partial()`。

**`adopt` 的 service 实现**（`service.ts`，唯一有实质逻辑的地方，其余为薄 CRUD）：解析 `alternatives` JSON → 找不到该 `alternativeId` 返 404；把当前 `text` 作为新候选 push 回数组、目标项从数组移除并写入 `text`、目标项原 `note` 保留；数组重新序列化为字符串。数组为空时字段存 `null` 而非 `"[]"`。

**`generate` 的 prompt 输入**（`service.ts` 的 `buildScriptPrompt`）：

1. `scene` 与 `SCENE_TEMPLATES` 的槽位序列（要求逐槽输出一段）
2. `title` + 用户 `brief`（要点，≤4000 字）
3. 字数预算 = `targetSec` × `wpm` ÷ 60，明确写「每段不超过 N 字」
4. `contentId` 有值时带 `ContentItem.coreMessage` 与 `outline`（须校验归属当前用户）
5. `BrandProfile` 单例存在时带 `toneOfVoice` / `personaTags` / `targetAudience`——让口播稿天然贴已定人设，只多一次 `findUnique`

system prompt 要求**只返回 JSON**：`{ "title": string, "beats": [{ "kind": BeatKind, "text": string, "cue"?: string }] }`。返回体用 `generatedScriptSchema`（zod）解析，`kind` 不在枚举内视为解析失败。响应附 `model` 字段供前端显示来源。

**`lib/llm.ts` 抽取**（本次唯一的既有代码改动）：

```ts
// packages/api/src/lib/llm.ts
export interface LlmProvider { baseUrl: string; apiKey: string; model: string }
export function getLlmProvider(): LlmProvider | null;   // 读 MELOG_LLM_*，含 http/https 校验
export function isLlmConfigured(): boolean;
export interface CompleteChatOptions {
  system: string; user: string; temperature?: number;
  timeoutMs?: number; fetchImpl?: typeof fetch;
}
export async function completeChat(options: CompleteChatOptions): Promise<string>; // 返回 content 原文
```

`modules/melog/llm.ts` 删除自身的 `providerSchema` / `LlmProvider` / `getLlmProvider` / `isLlmConfigured` 与 fetch 调用，改为 `import { completeChat } from '../../lib/llm.js'`；保留 MeLog 专属的 `gatherContextData` / `SKILL_INSTRUCTIONS` / `buildSkillPrompt` / `generateLlmReport`（后者内部改用 `completeChat`，`summary` 首行提取逻辑留在 MeLog 侧）。调用点直接改 import，不加 re-export 兼容层。`melog/llm.test.ts` 与 `melog/routes.test.ts` 必须保持绿色。

### 提词器

从 `ScriptEditor` 的「进入提词」挂载为 `fixed inset-0 z-50` 覆盖层，**不是路由**，退出回到编辑器。

- 一次只显示一个 beat（念稿按段推进，不做连续滚动），字号 `clamp(28px, 5vw, 64px)`，`cue` 以弱化小字显示在段上方
- 控制：`空格` 暂停/继续、`←/→` 上一段/下一段、`+/-` 调速、`ESC` 退出
- 自动滚动按 `wpm` 换算的字/秒推进；段内超出视口时容器内滚动
- 底部进度条：当前段序号/总段数、已用时长 / `targetSec`；`targetSec` 超时后计时转红
- 退出时 toast 本次实际用时，不写库

## 6. 自动化行为

1. **选题带出**：编辑器选 `contentId` 后，前端从已加载的 `/brand/contents` 结果取该条的 `title` / `coreMessage` / `outline`。若当前稿的 beats 全为空，则按**本稿 scene 的模板**填槽：`title` 进稿头、`coreMessage` 进 `hook`、`outline` 进 `value`；模板中不含该 kind 时跳过对应写入（`talk` 无 `hook`，故只落 `value`），且仅**提示**用户可「AI 展开」，不自动调 LLM
2. **场景切换**：`scene` 改动时若已有非空 beats 需二次确认，确认后按新模板重排（不销毁已写文本，多余段落 `body`）
3. **状态推进**：`status` 无自动流转（台词稿不进发布链）。提词器退出时若全部 beats 有文本且仍为 `draft`，提示可置 `ready`；用户实际用过一次后置 `used` 由手动完成
4. **语速缺省**：`wpm` 为空时，时长计算与提词器取 `DEFAULT_WPM_BY_SCENE[scene]`，不写回数据库

## 7. 错误处理

与 brand 模块一致，复用其 `handleError(fastify, error, reply)` 写法（`z.ZodError` → 400 带字段信息；其余 → 500 + `fastify.log.error`）：

- 改删一律 `updateMany` / `deleteMany` 带 `userId`，影响 0 行 → 404
- beat 与其子操作（PATCH / adopt / 整序）先按 `id + userId`（beat 经 `script.user` 关联）校验归属，不匹配 → 404
- `contentId` 不属当前用户 → 400 `{ error: '选题不存在' }`（沿用 brand 对 `topicId` / `pillarId` 的 `assertRefOwned` 处理口径，取明确报错而非静默忽略）
- `alternatives` JSON 解析失败（脏数据）→ service 视作空数组并在 PATCH 时重写为合法值，不抛 500
- `POST /scripts/generate`：LLM 未配置 → 503 `{ error: 'LLM 未配置，需要 MELOG_LLM_BASE_URL / MELOG_LLM_API_KEY / MELOG_LLM_MODEL' }`；端点非 2xx 或超时 → 502；返回体不合 schema → 502 `{ error: '模型输出无法解析，请重试或改用手工填写' }`。生成失败不落库、不改已有稿

## 8. 测试策略

`packages/api/src/modules/script/routes.test.ts`，模式仿 `modules/brand/routes.test.ts`。覆盖：

- CRUD：按 `scene` / `status` / `contentId` / `q` 筛选；创建带 `beats` 的稿能一次拿到有序段

- 回归：`melog/llm.test.ts` 在抽取后仍绿（这是本次唯一碰既有代码的地方）
